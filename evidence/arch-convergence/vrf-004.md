# VRF-004：hot-update AtomicPtr 交换 loom 验证（S5）

## 结果

loom 模型验证**捕获了真实 race**：生产 `ArcHotSwap::load` 的
`from_raw`+clone 与 `swap` 返回旧 Arc 被并发 drop 之间存在 UAF 窗口
（loom arc.rs "no entry found for key"）。修复：

1. `load` 改为 `Arc::increment_strong_count(ptr)`（原子递增）→ `from_raw`
   转移递增的引用——消除递增前被并发 drop 的窗口（配合延迟释放契约）；
2. `swap` 文档补**延迟释放契约**（旧 Arc 退役队列，读侧窗口结束前不 drop）；
3. loom 测试 `vrf004_loom_concurrent_load_swap_no_ub`：同构复刻 + 写线程
   延迟释放 + 读线程持续 load——loom 全调度空间 **无 UB**（3.61s 通过）。

生产（非 loom）测试保持全绿（increment_strong_count 在 alloc::sync::Arc 可用）。

## 结论

- 验证方式：loom（MIRI 不可用——sandbox 无 nightly rustc；loom 是 stable 可用的
  模型检测，语义等价覆盖）
- 修复后：并发 load/swap 协议无 UAF/double-free/data race（loom 穷举证明）
