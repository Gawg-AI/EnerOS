## 1. 执行摘要

EnerOS 的目标不应被定义为“让 LLM 根据很多数据生成控制命令”，而应定义为：

> 在明确的信任域、时间域、权限域和资源域内，把异构事实冻结为可追溯的可信决策快照；让规则、预测模型、LLM 和求解器在各自授权范围内产生候选结果；再由独立认证模块验证安全性、可行性、时效性和可执行性，只有认证后的计划才能进入具有幂等、回读和收敛能力的控制链。

本设计采用以下不可破坏的产物链：

```text
ObservedEvent
  → AcceptedEvent
  → TrustedDecisionSnapshot
  → ValidatedObjective
  → CandidatePlan
  → CertifiedPlan
  → CommandBatch
  → ExecutionReceipt
  → ReconciledOutcome
```

每一种产物只能由一个拥有明确职责的深模块创建。后续模块只接受上一阶段的合法类型，不接受自然语言、任意 JSON、裸浮点数或缺少证据的数据。这是系统正确性的主骨架。

核心判断：

1. **LLM 不承担最终正确性。** LLM 只生成有证据引用的类型化意图、解释和候选方案，不拥有设备控制能力。
2. **求解器不承担全部正确性。** 求解器给出候选计划；独立认证模块必须复算硬约束、数值残差、设备能力和安全包络。
3. **规则不等同于散落的 `if`。** 规则必须版本化、分级、可追溯、可回放，并明确硬约束与软偏好。
4. **“发送成功”不等于“执行正确”。** 只有设备回读满足预期且系统状态收敛，才能产生 `ReconciledOutcome::Achieved`。
5. **云端或企业端不可替代站端安全。** 保护、联锁、租约、限幅、紧急停机和最终控制权必须保留在站端或 PLC/SIS。
6. **扩展通过稳定 seam 完成。** 新协议、新市场、新模型、新求解器和新设备通过 adapter 接入，不把差异泄露到所有调用方。

## 2. 现状代码基线

本节只用于确定迁移起点，不把当前实现描述成目标能力。

### 2.1 当前已经存在、可以深化的基础

- 协议实现和点表框架：`crates/protocols/*`、`crates/runtime/config-bundle/*`。
- 遥测可信校验：`crates/ai/safety-validator/src/trusted.rs`。
- LLM 意图、双脑协调和求解器相关模块：`crates/ai/intent-contract/*`、`crates/ai/dual-brain/*`、`crates/ai/solver-core/*`。
- 控制授权、租约、fencing、SBO、审计、协议写入及回读：`crates/protocols/control-gateway/*`、`crates/protocols/control-dispatch/*`。
- 市场、VPP、联邦、数字孪生等领域算法模块：`crates/agents/*`、`crates/scenarios/*` 中的相关 crate。

### 2.2 当前生产链的主要限制

- 实际统一遥测入口主要是 Modbus TCP；其他协议尚未汇入同一个可信状态面。
- 点表存在固定规模限制，可信状态使用固定字段和固定长度 IPC。
- 当前 AI worker 主要输出单个功率值；完整计划、设备绑定和真实求解状态会丢失。
- 本地 LLM/HiGHS 并未进入默认产品 profile 的实际闭环。
- 市场、联邦、VPP、企业工艺数据未汇入统一决策快照。
- 控制幂等状态在真实设备写入和回读之前被标记为 Applied，必须重构执行状态机。
- 连续功率设定与开关命令语义、反馈单位和保护反馈映射仍有不一致。

因此，迁移策略必须是“保留有价值的实现，重建统一产物链和深模块 seam”，而不是继续在现有固定快照上添加字段。

### 2.3 2026-09-22 实现对照（仅列已核源码的事实）

| 设计链环节 | 已存在的代码事实 | 尚不可由此推出的结论 |
|---|---|---|
| 采集事实与来源门 | `telemetry-model::event::ObservationEvent`；`ingestion-core::SourceRegistry`；`protocol-services::ingestion_stage`；Modbus TCP、IEC104 的 EL0 服务源码存在 | “所有协议与业务源都已生产接通同一快照”或所有真实对端互操作通过 |

## 3. 目标、非目标与设计原则

### 3.1 目标

1. 支持协议、市场、工艺、企业和联邦数据的持续扩展。
2. 支持不同数据速率、时间语义、质量等级和安全等级。
3. 支持规则、预测模型、LLM、数学求解器和人工审批的组合决策。
4. 任何进入控制链的计划都可验证、可追溯、可撤销或可补偿。
5. 任一外部依赖失败时都有明确降级模式、禁止事项和恢复条件。
6. 控制链在断网、模型不可用、数据不完整和求解超时情况下仍保持安全。
7. 同一历史输入、配置和模型版本能够重放并解释当时决策。
8. 支持站点内自治、企业级协调和联邦级能力协商，同时避免把全部原始数据集中到一个全局大模型。

### 3.2 非目标

- 不让 LLM 直接控制断路器、PLC、PCS、充电桩或工业设备。
- 不承诺在不可靠网络和不支持幂等的设备上实现物理意义的 exactly-once。
- 不把保护系统、SIS 或 PLC 硬联锁迁移到通用 AI 平台。
- 不要求所有数据进入同一个数据库、同一种 schema 或同一保留周期。
- 不把“求解器返回 Optimal”当成执行正确性的充分条件。
- 不用一个全球单体求解问题替代分层资源协调。

### 3.3 原则

1. **安全优先于收益，事实优先于推断，站端约束优先于云端目标。**
2. **默认拒绝。** 缺数据、过期、版本不一致、来源不可信、无法验证时不产生新控制动作。
3. **数据与指令分离。** 外部输入一律视为数据，不能携带可执行指令语义穿透模型 harness。
4. **快慢环分离。** 保护、设备控制、站级优化、企业/市场计划分别运行在不同时间尺度。
5. **控制面与分析面分离。** 高频波形和历史分析不能阻塞实时控制总线。
6. **不可变决策输入。** 一次决策只引用一个冻结的 `TrustedDecisionSnapshot`。
7. **类型表达权限。** 能否构造某种产物类型，代表模块是否拥有相应权限。
8. **独立验证。** 计划生成者不能同时成为最终认证者。
9. **可观察降级。** 降级不能静默发生，必须产生原因、作用域、到期时间和恢复条件。
10. **局部自治、分层协调。** 站点发布能力包和承诺，不默认上传全部设备原始遥测。

## 4. 统一领域语言

以下术语是本架构的规范用语。实现、配置、日志和测试不应为同一概念创造第二套名称。

| 术语 | 定义 | 明确不是什么 |
|---|---|---|
| `ObservedEvent` | adapter 从外部源观察到的原始事实，尚未获得系统信任 | 可信遥测、控制指令 |
| `AcceptedEvent` | 已通过来源、schema、时间、单位和基本质量门禁的不可变事件 | 已完成业务融合的状态 |
| `TrustedDecisionSnapshot` | 针对一次决策作用域，在确定事件时间切面冻结的事实、拓扑、能力、规则、预测和证据集合 | 实时数据库的任意查询结果 |
| `ObjectiveCandidate` | 操作员、市场、规则或 LLM 提出的目标候选 | 可以执行的计划 |
| `ValidatedObjective` | 已通过权限、词汇、范围、冲突和硬策略验证的目标 | 求解结果 |
| `CandidatePlan` | 规则、启发式或求解器生成的候选时序资源计划 | 已认证、可执行计划 |
| `CertifiedPlan` | 独立认证模块确认安全、可行、可授权、未过期且可绑定到真实资源的计划 | LLM 或求解器可直接创建的对象 |
| `CommandBatch` | 从 `CertifiedPlan` 编译得到的有序、类型化、带前置条件的设备命令集合 | 任意协议报文集合 |
| `ExecutionReceipt` | 命令在持久化、授权、发送、传输 ACK、设备 ACK、回读等阶段的事实记录 | 最终业务目标已经达成 |
| `ReconciledOutcome` | 将回读状态与计划预期比较后形成的最终结果 | 发送成功 |
| `CapabilityEnvelope` | 某资源或站点在时间窗口内可承诺的功率、能量、爬坡、可用性和不确定性边界 | 原始遥测全集 |
| `Commitment` | 一个主体对外接受的、带时窗和违约语义的资源交付责任 | 内部优化建议 |
| `HardConstraint` | 任何情况下都不得由优化收益覆盖的安全、物理、法规、工艺或合同约束 | 权重很高的软目标 |
| `SoftObjective` | 可以权衡、降级或放弃的成本、收益、碳排、寿命等优化目标 | 安全限制 |
| `GateEvidence` | 某门禁对输入、规则版本、判断结果和原因生成的不可变证据 | 普通调试日志 |
| `DegradationLease` | 允许系统在明确作用域、能力上限和到期时间内运行降级策略的授权 | 永久关闭检查的开关 |

### 4.1 计划、策略、命令和结果必须区分

- **策略**：描述决策原则，例如“在不突破需量上限时优先消纳光伏”。
- **计划**：描述资源在未来时段的目标轨迹。
- **命令**：描述某台设备在某个时刻执行的具体动作。
- **结果**：设备实际状态及业务目标是否达成。

禁止使用一个 `power_kw: f64` 同时表达以上四个概念。

## 5. 正确性的定义

系统不能承诺抽象的“绝对正确”，但必须定义可验证的正确性契约。一个输出只有同时满足以下条件，才能被称为“正确执行结果”：

1. **语法正确**：schema、枚举、维度、单位和数值均合法。
2. **来源正确**：身份、签名、序号、租户、站点和权限均可信。
3. **时间正确**：输入未过期，时钟状态满足本次决策要求。
4. **语义正确**：连续设定、离散开关、模式切换、复位等命令类型不混淆。
5. **约束正确**：所有硬约束均满足，且有独立复算证据。
6. **不确定性可接受**：对预测误差、数据缺失和通信抖动保留足够安全裕度。
7. **授权正确**：计划、操作者、租约、fencing token 和资源所有权匹配。
8. **绑定正确**：抽象资源已解析为真实设备、点位、单位、量程和协议动作。
9. **执行正确**：命令按照状态机持久化、发送并获得预期设备反馈。
10. **结果正确**：回读状态在容差和稳定窗口内达到计划目标。
11. **可追溯**：输入、规则、模型、求解器、配置和执行证据可以重放。

任何一项不满足，结果必须是 `Rejected`、`Failed`、`Indeterminate` 或 `PartiallyAchieved`，不得伪装成 `Committed` 或 `Achieved`。

## 6. 时间尺度和控制权边界

| 层级 | 典型周期 | 职责 | 允许的决策方式 | 最终控制权 |
|---|---:|---|---|---|
| L0 保护层 | 微秒～10 ms | 保护、硬联锁、紧急停机 | 继保、SIS、PLC 固化逻辑 | 设备/保护装置 |
| L1 设备与快速控制层 | 10 ms～1 s | 限幅、爬坡、模式保持、局部闭环 | 确定性规则、控制器、经过验证的 MPC | 站端控制器 |
| L2 站级调度层 | 1 s～15 min | 多设备分配、SOC、需量、工艺协调 | 规则、预测、LP/QP/MILP/MPC | 站端执行模块 |
| L3 企业/市场层 | 5 min～数日 | 市场、合同、跨站资源协调 | 求解器、场景分析、LLM 辅助 | 只能下发承诺/目标边界 |

上层不得直接绕过下层。L3 只能下发 `Commitment` 或 `ValidatedObjective`；L2 必须结合站端最新快照重新求解；L1/L0 保留否决权。

## 7. 信任域和部署边界

### 7.1 五个信任域

1. **外部不可信域**：市场接口、互联网、第三方模型、联邦节点、操作员文本和外部文件。
2. **协议隔离域**：解析协议、限制资源、验证身份、隔离畸形报文和重放攻击。
3. **可信数据域**：事件日志、schema/语义目录、状态物化、质量和 provenance。
4. **决策沙箱域**：预测、LLM、求解器和场景计算；无设备控制能力。
5. **认证控制域**：计划认证、租约、授权、命令编译、协议写入、回读和对账。

跨域只能传递明确类型和签名/摘要，不能传递共享可变对象。

### 7.2 推荐部署形态

```text
企业/云端
  ├─ 市场与合同接入
  ├─ 企业规则与工艺目标
  ├─ 跨站协调优化
  ├─ 模型注册、评测和发布
  └─ 审计与离线分析
          │ 仅传递目标、能力包、承诺和模型制品
          ▼
站端
  ├─ 协议接入与隔离
  ├─ 站端事件日志和可信状态
  ├─ 站级预测与优化
  ├─ 计划认证与执行 Saga
  ├─ 本地 HMI/人工接管
  └─ 断网自治
          │ 类型化命令 + 前置条件
          ▼
设备/PLC/SIS
  ├─ 硬联锁与保护
  ├─ 最终限幅和模式检查
  └─ 实际执行及独立反馈
```

## 9. 深模块与稳定 seam

以下是概念接口，不要求照抄为 Rust 语法。接口还包括错误模式、时序、性能、版本兼容和安全不变量。

### 9.1 `IngestionModule`

```text
ingest(SourceFrame) -> IngestReceipt
```

模块内部隐藏：协议解码、来源认证、去重、schema 选择、单位规范化、质量映射、事件时间、背压、隔离和证据写入。

adapter 示例：Modbus TCP、IEC104、MMS、GOOSE、SV、MQTT、CAN、DL/T 645、市场接口、MES/ERP、联邦节点和测试回放。

调用方不应知道寄存器地址、IEC quality bit 或 MQTT topic；这些差异只存在于 adapter 与语义映射配置中。

### 9.2 `SnapshotModule`

```text
freeze(DecisionScope, EventTimeCut)
  -> TrustedDecisionSnapshot | SnapshotRejection
```

模块内部隐藏：watermark、迟到数据、多速率 join、来源冲突、拓扑解析、能力计算、缺失策略、预测绑定、版本冻结和 provenance Merkle root。

### 9.3 `ObjectiveModule`

```text
validate(ObjectiveCandidate, TrustedDecisionSnapshot)
  -> ValidatedObjective | ObjectiveRejection
```

候选目标可来自规则、市场、操作员或 LLM，但最终都经过同一接口。模块负责权限、目标词汇、优先级、冲突、作用域、时窗和硬规则检查。

### 9.4 `PlannerModule`

```text
plan(TrustedDecisionSnapshot, ValidatedObjective, PlanningBudget)
  -> CandidatePlan | PlanningFailure
```

adapter 可以是确定性启发式、LP、QP、MILP、MPC、CP-SAT、鲁棒优化或测试求解器。选择哪个 adapter 是模型注册和风险策略的一部分。

### 9.5 `CertifierModule`

```text
certify(TrustedDecisionSnapshot, CandidatePlan)
  -> CertifiedPlan | CertificationRejection
```

`CertifiedPlan` 的构造器只能在该模块内部可见。模块独立复算硬约束、数值残差、安全裕度、设备能力、计划时效、绑定完整性和降级资格。

### 9.6 `ExecutionModule`

```text
execute(CertifiedPlan) -> ExecutionReceipt
reconcile(ExecutionReceipt, FeedbackWindow) -> ReconciledOutcome
```

模块内部隐藏：持久 outbox、业务幂等、授权、防重放、租约、fencing、SBO、命令编译、协议发送、重试、回读、补偿和状态收敛。

### 9.7 seam 纪律

- 每个外部 seam 至少有生产 adapter 和可重复测试 adapter。
- 测试通过同一个接口观察结果，不穿透接口断言内部状态。
- 协议 adapter 不承载业务决策；Planner adapter 不承载最终安全认证。
- 新设备、新协议和新求解器不得要求修改所有调用方。
- 删除某个深模块后，如果复杂度会扩散到多个调用方，说明该模块具有足够 depth；纯转发模块应合并。

## 10. 数据架构

### 10.1 数据类别

| 类别 | 示例 | 典型时效 | 推荐存储/传输策略 |
|---|---|---:|---|
| 实时测量 | 电压、电流、功率、频率、SOC、温度、流量、压力 | ms～s | 分区事件流 + 时序状态 |
| 状态与 SOE | 开关、模式、保护动作、告警、人工接管 | ms～s | 不可丢事件流，高优先级 |
| 高频波形 | 故障录波、谐波、振动波形 | μs～ms | 对象/块存储，事件只携带引用和摘要 |
| 资产与拓扑 | 站点、母线、线路、设备、能力曲线 | 小时～月 | 版本化主数据与图模型 |
| 市场与合同 | 价格、出清、辅助服务、偏差、合同 | 秒～日 | 版本化业务事件和曲线 |
| 工艺与生产 | 订单、配方、工序、班次、质量约束 | 秒～日 | 业务事件 + 约束制品 |
| 预测 | 负荷、光伏、风电、价格、健康度 | 分钟～日 | 带置信区间和模型版本的预测制品 |
| 联邦能力 | 能力包、承诺、可用性、不确定度 | 秒～小时 | 签名的聚合制品，不默认共享原始数据 |
| 治理证据 | 来源、签名、schema、规则、模型、审批 | 全周期 | 防篡改证据存储 |

### 10.2 统一事件信封

每个 `AcceptedEvent` 至少包含：

```text
event_id
tenant_id / organization_id / site_id
source_id / source_epoch / sequence
asset_id / resource_id / point_id
event_kind / schema_id / schema_version
event_time / ingest_time / monotonic_time
value + unit + dimension
quality + uncertainty + missing_reason
mapping_version / calibration_version
source_identity / integrity_proof
trace_id / correlation_id
raw_evidence_ref
```

不允许使用 `source = 1`、`mapping_version = 1` 等硬编码值替代来源注册表。

### 10.3 Schema 与语义目录

`SchemaRegistry` 负责结构兼容；`SemanticCatalog` 负责业务含义。两者必须分开：

- schema 解决“字段能否解码”。
- 语义目录解决“这是电池 SOC 还是百分比状态、单位是 ratio 还是 percent、控制方向是什么”。

语义目录至少管理：量纲、工程单位、量程、控制类型、读写权限、反馈映射、资产归属、拓扑关系、校准、危险等级和数据所有者。

### 10.4 事件时间与多速率融合

- 每个源维护 watermark、最大乱序时间和时钟健康度。
- 快照按事件时间形成，不按“最后一次数据库查询”形成。
- 快照必须记录缺失、迟到、冲突和插值，不能静默补零。
- 高频、低频和业务数据使用各自窗口策略。
- 跨站协调在时钟失同步时自动缩小作用域或拒绝。
- 快照一旦创建即不可变；新事件只能形成新快照。

### 10.5 数据优先级与背压

建议至少分四级：

1. P0：保护、SOE、控制回执、人工接管；不得因分析流量丢弃。
2. P1：控制必需遥测；允许有限聚合，不允许静默丢失。
3. P2：普通监测和预测输入；允许采样、降频和延迟。
4. P3：波形、历史回填和离线分析；不得抢占控制资源。

每个分区必须声明容量、最大排队时间、丢弃策略和告警阈值。不能使用一个全局固定长度缓冲承载所有数据等级。

### 10.6 数据生命周期

原始证据、规范事件、当前状态、决策快照和分析数据具有不同保留期。删除、归档和脱敏策略按数据分类执行，不能把控制审计证据与普通遥测一起过期。

## 11. 可信决策快照

`TrustedDecisionSnapshot` 是数据面与决策面的唯一 seam。建议包含：

- `snapshot_id`、作用域、创建时间、事件时间切面和有效期。
- 规范化测量与状态，以及每个值的质量、来源和不确定度。
- 版本化资产拓扑、设备能力、维护状态和人工接管状态。
- 当前租约、fencing token、已接受承诺和未完成命令。
- 企业规则、工艺约束、市场约束和安全策略的摘要。
- 预测分布、置信区间、适用时间窗和模型版本。
- 缺失点、冲突点、降级点和不可观测区域。
- 完整 provenance root 与用于重放的证据引用。

快照形成规则：

1. 必需事实缺失时返回 `SnapshotRejection`，不得自动补默认值。
2. 可选事实缺失时必须降低能力包或扩大安全裕度。
3. 过期时间由决策类型决定，不能全局统一。
4. 对市场计划、站级控制和保护分析分别建立不同 scope。
5. 任何计划都绑定唯一 `snapshot_id` 和 `snapshot_digest`。

## 12. 混合决策架构

### 12.1 决策职责矩阵

| 机制 | 负责 | 禁止 |
|---|---|---|
| 硬规则 | 安全、法规、工艺联锁、权限、数据质量、设备限值 | 被收益权重覆盖 |
| 软规则 | 运营偏好、优先级、经验阈值、降级启发式 | 伪装成物理硬约束 |
| 预测模型 | 负荷、新能源、价格、健康度和不确定度预测 | 直接授权设备动作 |
| LLM | 文本解析、目标澄清、证据检索、方案解释、异常归因 | 数值可行性证明、直接发命令 |
| 数学求解器 | 时序优化、资源分配、网络/工艺/市场约束 | 自行决定数据是否可信 |
| 数字孪生 | what-if、动态响应和风险验证 | 替代现场硬联锁 |
| 人工审批 | 高风险授权、规则变更、异常处置 | 替代系统证据和回读 |

### 12.2 目标优先级

建议采用严格字典序，而不是把所有东西简单加权：

1. 人身和设备安全。
2. 法规、并网、工艺不可违反条件。
3. 已签署合同和市场承诺。
4. 供能连续性与生产任务。
5. 经济性、碳排、寿命和舒适度。

只有同一级目标之间才允许权重或 Pareto 权衡。安全不能因为电价收益更高而被优化器“买掉”。

### 12.3 分层优化

- 企业/联邦层求解站点间承诺和能力分配。
- 站点层用最新本地快照把承诺分解到资源。
- 设备层执行短时轨迹并应用本地限幅。
- 任一下层发现不可行，必须返回新的能力包或 `CommitmentAtRisk`，不能盲目执行上层目标。

这避免一个全局模型因数据量、网络延迟或局部故障失去可用性。

### 12.4 目标和控制权仲裁

多个主体可能同时提出互相冲突的目标，因此必须由确定性的 `CommandArbiter` 仲裁，不能采用“最后一条消息获胜”。建议优先级如下：

1. 设备保护、SIS 和硬联锁。
2. 现场紧急停机与安全处置。
3. 有有效租约的本地人工接管和检修隔离。
4. 调度机构的强制指令、已接受的市场/合同承诺。
5. 站级安全运行和工艺连续性目标。
6. 企业成本、碳排和跨站协调目标。
7. 优化建议与 LLM 建议。

仲裁不仅比较优先级，还必须检查作用域是否重叠、租约是否有效、命令是否可合并、旧计划是否需要撤销、以及是否会造成新的承诺风险。LLM 永远不参与控制权优先级裁决。

## 13. 模型 Harness、Skill 和有界 Loop

### 13.1 三者的职责

| 机制 | 定位 | 是否安全边界 |
|---|---|---|
| Skill | 版本化的任务方法、提示模板、工具使用说明和领域步骤 | 否，只是行为配方 |
| Loop | 在一次任务内迭代“提出—检查—修正”的工作流 | 否，除非被 harness 限制 |
| Harness | 包裹模型的权威运行时，限制输入、输出、工具、预算、版本和证据 | 是，模型与系统之间的强制 seam |

结论：可以使用 skill 和 loop，但它们必须运行在 harness 内。skill 不能代替安全策略，loop 不能无限自治。

### 13.2 `ModelHarness` 输入门禁

模型不能直接读取整个数据库或任意文档。`ContextPackBuilder` 根据任务生成最小输入包：

- 绑定 `snapshot_id`、租户、站点、任务和数据分类。
- 仅允许来自签名、版本化、已批准知识源的内容。
- 明确区分 system policy、可信规则、普通事实和外部不可信文本。
- 外部文本按“数据”转义，防止把 prompt injection 当成指令。
- 敏感数据按最小权限脱敏。
- 输入 token、记录数、时间范围和不确定度有明确预算。
- 所有引用带 `evidence_ref`，禁止模型伪造来源。

### 13.3 运行时约束

- 固定模型、权重、量化、prompt、skill、tool schema 和 harness 版本。
- 按风险等级设置 token、时间、迭代次数、工具调用次数和并发预算。
- 工具采用 capability allowlist；默认只有只读查询和候选提交能力。
- 模型进程运行在资源和网络隔离的沙箱中。
- 每次工具调用重新检查租户、作用域、参数 schema 和数据分类。
- 禁止模型访问协议写入、控制网关、私钥、规则发布和模型发布能力。
- 任何超时、预算耗尽或异常都返回显式 `Abstain`，不能补默认命令。

### 13.4 有界 Loop

推荐 loop：

```text
理解目标
  → 选择证据
  → 生成 ObjectiveCandidate
  → 结构/证据检查
  → 最多 N 次修正
  → 提交或 Abstain
```

每轮必须保持以下不变量：

- 不改变任务作用域。
- 不扩大工具权限。
- 不把外部文本升级为系统规则。
- 不直接生成 `CertifiedPlan` 或 `CommandBatch`。
- 不因前一轮失败而放宽硬约束。
- 达到预算、重复状态或无新证据时终止。

### 13.5 输出门禁

LLM 只允许输出封闭 schema，例如：

```text
ObjectiveCandidate {
  objective_kind,
  scope,
  valid_from,
  valid_until,
  priorities,
  requested_bounds,
  assumptions,
  evidence_refs,
  uncertainty,
  abstain_reason
}
```

随后依次执行：结构校验、枚举白名单、单位校验、证据存在性、权限、时间窗、规则冲突和目标可满足性预检。任何额外字段或无法解释的自由文本不能进入规划器。

### 13.6 模型动作风险等级

| 等级 | 示例 | 处理方式 |
|---|---|---|
| A0 | 解释、检索、报表 | 可自动执行只读任务 |
| A1 | 建议目标、异常归因 | 输出建议，不产生计划 |
| A2 | 低风险、可逆的候选目标 | 经规则、求解和认证后可自动化 |
| A3 | 高影响调度、市场承诺 | 认证后仍需双人或策略审批 |
| A4 | 保护定值、紧急跳闸、绕过联锁 | 禁止 LLM 发起或修改 |

### 13.7 模型生命周期

模型、prompt、skill、检索语料和 harness 必须作为一个完整制品发布：

```text
开发 → 离线评测 → 对抗测试 → 历史回放 → HIL → 影子运行 → 小流量 canary → 生产
```

发布制品必须签名，包含风险等级、适用任务、输入 schema、输出 schema、评测集摘要、已知限制、资源预算和回滚版本。任何单独替换 prompt 或 skill 都视为模型变更。

## 14. 求解器与优化模型约束

### 14.1 求解输入

求解器只能接收从可信快照和已验证目标编译的 `OptimizationProblem`，至少包含：

- 时间网格和作用域。
- 资源能力、拓扑和设备可用性。
- SOC、热、爬坡、启停、最小运行时间和效率曲线。
- 电网功率平衡、需量、潮流或线路容量约束。
- 工艺依赖、生产窗口和不可中断任务。
- 市场承诺、价格、偏差和备用容量。
- 预测分布、场景和安全裕度。
- 所有硬约束来源与版本。

### 14.2 求解输出

`CandidatePlan` 必须保留：

- 完整时序和每个资源的绑定，不得只取第一个功率点。
- `Optimal / Feasible / Infeasible / Unbounded / Timeout / NumericalError` 原始状态。
- objective 分解、gap、残差、边界违反、求解耗时。
- 输入摘要、模型摘要、约束摘要、求解器版本和随机种子。
- 采用的降级、松弛变量和未满足软目标。
- 备用计划和触发条件。

不得把 `Timeout` 或 `Suboptimal` 重写为 `Optimal`，不得用零值填补缺失解变量。

### 14.3 独立认证

认证模块使用独立实现复算：

1. 类型、单位和时间网格。
2. 物理平衡与设备能力。
3. 所有硬约束和授权边界。
4. 数值残差与容差。
5. 预测不确定性下的安全裕度。
6. 与当前未完成命令和已接受承诺的冲突。
7. 计划有效期和最新快照差异。

高风险计划还应经过数字孪生或 HIL 场景验证。验证器与生成计划的求解器不能共享同一套“默认补值”逻辑。

## 15. 全链路门禁

| Gate | 输入 → 输出 | 必查内容 | 失败结果 |
|---|---|---|---|
| G0 制品门禁 | 配置/规则/模型 → 已批准制品 | 签名、版本、兼容性、审批、回滚 | 禁止加载 |
| G1 来源门禁 | SourceFrame → ObservedEvent | 身份、租户、来源 epoch、速率、重放 | 隔离/拒绝 |
| G2 数据门禁 | ObservedEvent → AcceptedEvent | schema、单位、范围、时间、质量、完整性 | 拒绝/降质 |
| G3 快照门禁 | 事件集合 → TrustedSnapshot | 覆盖、新鲜、冲突、拓扑、可观测性 | 拒绝/缩域 |
| G4 目标门禁 | ObjectiveCandidate → ValidatedObjective | 权限、范围、证据、硬策略、冲突 | 拒绝/需审批 |
| G5 模型门禁 | ContextPack → 模型输出 | harness、工具、预算、封闭 schema | Abstain |
| G6 求解门禁 | 问题 → CandidatePlan | 状态、完整解、gap、残差、预算 | 失败/降级 |
| G7 认证门禁 | CandidatePlan → CertifiedPlan | 独立硬约束、安全裕度、绑定、有效期 | 拒绝 |
| G8 执行授权门禁 | CertifiedPlan → PendingExecution | RBAC、租约、fencing、SBO、资源预留 | 拒绝/排队 |
| G9 设备门禁 | Command → DeviceAck | 命令语义、量程、模式、本地联锁 | 拒绝/限幅 |
| G10 结果门禁 | Feedback → ReconciledOutcome | 回读、容差、稳定窗口、目标达成 | Failed/Indeterminate |

每个 Gate 必须输出 `GateEvidence`：输入摘要、规则版本、决定、原因码、时间和签名。日志文本不能代替 GateEvidence。

## 16. 执行状态机与结果正确性

### 16.1 状态机

```text
Proposed
  → Validated
  → Reserved
  → Persisted(Pending)
  → Authorized
  → Sent
  → TransportAcknowledged
  → DeviceAcknowledged
  → ReadbackVerified
  → Committed
  → Reconciled(Achieved | PartiallyAchieved | NotAchieved)
```

异常终态：

```text
Rejected       权限、策略、约束或输入不允许
Failed         已知未成功且影响已明确
Indeterminate  无法确认设备是否产生物理效果
Expired        尚未执行就已超过有效期
Compensating   正在执行补偿或重新优化
```

### 16.2 幂等与防重放

- `command_id`：一次具体发送尝试，用于安全防重放。
- `operation_id`：一次业务动作，用于幂等和生命周期查询。
- `plan_id`：计划身份，可包含多个 operation。
- `idempotency_key`：同一业务动作的稳定键。

这四者不得混用。幂等记录必须存储真实生命周期；以前的 `Rejected` 只能重放为 `Rejected`，`Pending` 只能查询或继续协调，`Indeterminate` 必须先对账，不能直接当作成功。

### 16.3 Outbox 与 Saga

- 在发送前持久化 Pending intent 和 outbox。
- outbox、审计证据和业务幂等状态必须原子提交。
- 发送 adapter 只能消费持久化 outbox。
- 多设备计划使用 Saga：资源预留、分步执行、验证、补偿或再优化。
- 不宣称跨真实设备的物理原子性。
- 对支持设备端幂等 token 的协议优先使用；不支持时依靠读前检查、回读和对账降低重复效果。

### 16.4 命令编译

`CommandBatch` 中每个命令必须包含：

- 目标资源、设备和控制点。
- 命令语义：连续设定、离散开关、模式、复位等。
- 规范单位和协议单位转换证据。
- 允许范围、爬坡、前置模式、有效期。
- 期望回读点、容差、超时和稳定窗口。
- operation、lease、fencing、授权和计划摘要。
- 失败后的补偿或安全动作。

协议 adapter 只负责确定性编码和传输，不重新解释业务意图。

## 17. 降级设计

降级不是“捕获异常后继续运行”，而是一个受授权、受时间限制、可观察的运行模式。

| 触发 | 检测 | 允许的降级 | 明确禁止 | 恢复条件 |
|---|---|---|---|---|
| 必需遥测缺失/过期 | G3 | 保持安全设定、缩小资源范围 | 新增长周期优化动作 | 连续健康窗口通过 |
| 来源冲突 | 质量引擎 | 隔离异常源，按批准的来源优先级运行 | 静默平均冲突值 | 人工/自动确认来源恢复 |
| 时间同步失效 | 时钟健康 | 本地单站、短时域控制 | 跨站协同、市场精确承诺 | 同步误差持续达标 |
| 事件流背压 | 队列指标 | 降采样 P2/P3，保留 P0/P1 | 丢弃 SOE、控制回执 | 队列和延迟回落并稳定 |
| 预测模型不可用 | 模型健康 | 持续性预测、保守区间 | 假装使用最新预测 | 回放检查和健康探针通过 |
| LLM 不可用/输出非法 | Harness | 规则 + 求解器或人工目标 | 用自由文本直接控制 | 模型健康和门禁重新通过 |
| 求解器超时 | G6 | 未过期的已认证计划、保守启发式 | 把 Timeout 标成 Optimal | 新计划认证成功 |
| 数字孪生不可用 | 验证健康 | 只允许低风险、可逆动作 | 高风险自动计划 | 仿真服务及基线恢复 |
| 市场接口中断 | 市场接入 | 履行已有承诺、站端经济运行 | 新报价/新承诺 | 对账并恢复序号连续性 |
| 云站网络分区 | 租约/心跳 | 站端自治和本地规则 | 过期远程命令 | 新 epoch、租约和状态同步 |
| 执行无回读 | G10 | 标记 Indeterminate、启动对账 | 盲目重复写入并报告成功 | 读取到确定状态或人工确认 |
| 策略/模型版本不匹配 | G0/G7 | 使用仍有效的旧签名版本 | 混用新旧约束 | 原子完成版本切换 |
| 资源过载 | 容量门禁 | 按风险和 QoS 排队/拒绝 | 保护任务与报表争抢资源 | 负载回到安全水位 |

每次降级生成 `DegradationLease`，必须包含原因、作用域、能力上限、开始时间、到期时间、批准者和退出条件。为避免正常/降级反复振荡，恢复使用滞回和连续健康窗口。

## 18. 可扩展性设计

### 18.1 分区

- 事件按 `tenant/site/source/resource/time` 组合分区。
- 快照和站级规划以 site 或 electrical island 为主要一致性作用域。
- 企业层只消费聚合状态、能力包和承诺。
- 热点资源可以独立分区，但同一控制对象只能有一个有效写租约。

### 18.2 横向扩展

- Ingestion adapter 可以无状态横向扩展；顺序通过 source partition 保证。
- 状态物化和 SnapshotModule 以作用域分片并维护主备。
- PlannerModule 是可调度计算池，按风险、deadline 和资源预算隔离。
- CertifierModule 独立扩展，不与 Planner 共用故障域。
- ExecutionModule 按站点部署，控制权不依赖云端水平扩展。

### 18.3 联邦扩展

联邦节点对外发布签名的 `CapabilityEnvelope`：

- 可用功率/能量区间。
- 时间分辨率、爬坡、持续时间和恢复时间。
- 不确定度、可靠性和当前承诺。
- 有效期、价格/成本边界和数据使用限制。

上级形成 `Commitment`，下级用本地快照重新分配。这样既降低数据量，也保留现场隐私、工艺秘密和自治能力。

### 18.4 容量规划

上线前必须用真实清单计算，而不是声称“海量”：

```text
event_rate = Σ(源数量 × 每源点数 × 采样频率)
storage_rate = Σ(event_rate × 编码大小 × 保留时间 × 副本数)
decision_load = Σ(决策作用域 × 决策频率 × 场景数 × 求解复杂度)
```

必须为每一类业务声明：持续/峰值事件率、P99 延迟、乱序窗口、允许丢失、恢复时间、计划 deadline 和最大控制抖动。固定数组可以保留在有硬实时上界的 L0/L1，但上界必须来自设备和安全论证，不能成为全平台规模限制。

### 18.5 一致性与可用性选择

- 同一设备的写租约、fencing token 和 operation 生命周期必须在站端具有单一顺序和强一致语义。
- 站内形成某个 `TrustedDecisionSnapshot` 时，其作用域内的版本和事件时间切面必须一致。
- 企业和联邦层的聚合状态采用最终一致；任何跨站视图都携带数据年龄和不确定度。
- 网络分区时优先保证站端安全和已授权的局部可用性，不维持虚假的全局一致。
- 云端恢复后先交换 epoch、未完成 operation、承诺和物理状态，再恢复自动协调。
- 灾备目标必须分别声明控制状态、审计证据、历史遥测和离线分析数据的 RPO/RTO；四者不能使用同一个模糊指标。

## 19. 安全与威胁控制

| 威胁 | 必要控制 |
|---|---|
| 伪造设备/市场/联邦数据 | 双向身份、签名、source epoch、序号、速率限制 |
| 数据投毒 | 来源隔离、多源交叉验证、漂移检测、人工复核 |
| Prompt injection | 上下文分级、外部文本数据化、工具白名单、封闭输出 |
| 模型供应链攻击 | 制品签名、SBOM、权重摘要、受控注册表、回滚 |
| 重放和越权命令 | command_id、租约、fencing、RBAC/ABAC、短 TTL |
| 协议写入劫持 | 独立控制网、最小能力、设备端门禁、回读 |
| 联邦节点失陷 | 最小共享、能力上限、信誉不是安全替代、可撤销身份 |
| 内部人员滥用 | 双人审批、职责分离、不可篡改审计、紧急访问到期 |
| 模型漂移/行为变化 | 影子评测、canary、运行时不变量、自动降级 |
| DoS/资源耗尽 | 分区、QoS、配额、deadline、隔离计算池和背压 |

密钥、模型发布、规则发布、控制授权和审计管理必须职责分离。任何超级管理员都不应单独拥有完整闭环权限。

## 20. 可观测性、证据与重放

### 20.1 全链路关联

以下标识贯穿事件、快照、模型、计划和命令：

```text
trace_id
snapshot_id
objective_id
plan_id
operation_id
command_id
model_run_id
gate_evidence_ids[]
```

### 20.2 必备指标

- 各来源事件率、迟到、重复、冲突、质量降级和时钟误差。
- 快照构建延迟、拒绝率、缺失原因和可观测范围。
- LLM abstain、schema 失败、证据失败、工具拒绝和预算耗尽。
- 求解状态、耗时、gap、残差、不可行原因和降级次数。
- 认证拒绝原因、计划过期、能力冲突和裕度分布。
- 执行各阶段延迟、重试、Indeterminate、回读偏差和补偿。
- 人工覆盖、规则变更、模型切换和降级租约。

### 20.3 决策重放

任何历史计划必须能使用原始证据引用、快照、规则、模型、求解器和随机种子在隔离环境中重放。重放结果需要区分：

- 完全确定性一致。
- 数值容差内一致。
- 因外部模型不可复现而只能验证已保存输出与后续门禁。

第三种情况不能用于最高风险自动控制。

## 21. 验证体系

### 21.1 设计时验证

- 对执行状态机、租约、fencing 和幂等语义建立形式化模型。
- 对每个深模块写接口契约、前置条件、后置条件和错误枚举。
- 对单位、时间、拓扑、能力和约束编译使用属性测试。
- 对协议和模型输入使用 fuzz、畸形报文、极值和 NaN/Inf 测试。
- 对求解模型使用小规模穷举或第二求解器做差分验证。

### 21.2 场景 Harness

建立统一 `ScenarioHarness`，输入一组版本化场景，驱动真实模块 seam：

```text
历史事件/合成故障
  → Ingestion adapter
  → SnapshotModule
  → ModelHarness/Planner
  → Certifier
  → 模拟或 HIL Execution adapter
  → ReconciledOutcome
```

场景至少包括：

- 多来源值冲突、单位错误、时钟漂移和序号重放。
- 市场高价但设备过温、SOC 过低、工艺不可中断。
- LLM prompt injection、虚假证据、越权目标和无限 loop 倾向。
- 求解不可行、Unbounded、Timeout、部分解和数值不稳定。
- 首次写入成功但 ACK 丢失、首次失败后同 operation 重试。
- 多设备部分成功、网络分区、租约过期和主备切换。
- 模型/规则/拓扑在计划生成后、执行前发生版本变化。
- 回读不一致、延迟达到、振荡和无法确定物理状态。

### 21.3 发布门禁

生产发布必须同时通过：

1. 接口契约测试。
2. 属性测试和 fuzz 基线。
3. 历史黄金场景回放。
4. 负载、背压、恢复和长稳测试。
5. 故障注入与网络分区测试。
6. HIL 设备语义和回读测试。
7. 模型/规则影子评测和风险审批。
8. 回滚演练和证据完整性检查。

测试“代码路径运行了”不够；验收必须断言最终 `ReconciledOutcome` 和所有安全不变量。

## 22. 规则、模型和配置治理

### 22.1 规则分级

- S0：设备/人身安全规则，只能由安全责任人双人审批。
- S1：法规、并网和工艺硬规则，需要领域负责人审批。
- S2：合同和运营策略，可由授权业务负责人发布。
- S3：软偏好和实验策略，可 canary，但仍受 S0～S2 约束。

规则必须有稳定标识、版本、作用域、单位、优先级、冲突策略、生效/失效时间、作者、审批、测试和回滚版本。

### 22.2 变更原子性

schema、语义映射、拓扑、规则、模型和设备 binding 不能独立“热改”后混合使用。通过 `DecisionBundle` 原子发布兼容版本集合；已有计划继续绑定旧 bundle，或因策略要求失效。

### 22.3 人工门禁

人工审批界面必须显示：

- 目标和作用域。
- 关键输入及缺失/不确定性。
- 硬约束验证结果。
- 计划前后状态、收益和最坏风险。
- 模型、规则、求解器和证据版本。
- 计划有效期和可撤销点。

禁止只显示一段 LLM 解释后让用户点击“批准”。

### 22.4 职责分离

| 角色 | 负责 | 不得单独完成 |
|---|---|---|
| 数据所有者 | 来源、质量、保留和数据授权 | 修改安全规则并发布模型 |
| 语义/资产所有者 | 单位、拓扑、设备能力和控制 binding | 批准自己的高风险 binding 变更 |
| 规则所有者 | 规则内容、等级、冲突和测试 | 绕过审批直接生产发布 |
| 模型所有者 | 训练、评测、已知限制和漂移 | 提升模型动作风险等级 |
| 优化所有者 | 数学模型、目标、求解器和数值验证 | 同时签发独立认证结论 |
| 安全责任人 | 硬约束、保护接口、风险分级和认证策略 | 修改收益目标后自行批准安全例外 |
| 运行人员 | 启停、人工接管、异常恢复和对账 | 永久关闭门禁或审计 |
| 审计人员 | 证据完整性和职责分离复核 | 操作生产控制 |

紧急访问必须有短 TTL、明确作用域、实时告警和事后复核，不能成为长期超级权限。

## 24. 分阶段落地

### Phase 0：修复当前控制正确性

目标：现有单站 Modbus 闭环先具备可信执行语义。

- 重构 Applied/Committed/Rejected/Indeterminate 状态和幂等记录。
- 分离 plan、operation、command 和 idempotency key。
- 修复连续功率/开关语义、电流越限、ramp、SOC 单位和反馈点冲突。
- proposal 保留完整计划、真实求解状态、目标资源和输入摘要。
- 真实验证 TTL、snapshot digest、计划 binding 和回读。

退出条件：首次失败后重试、ACK 丢失、回读失败和设备拒绝均产生正确终态；不存在未执行却 Committed。

### Phase 1：统一事件与语义数据面

- 建立 AcceptedEvent、来源注册、schema registry 和 semantic catalog。
- 所有协议采集经过统一 IngestionModule。
- 引入分区持久事件日志、QoS、背压、watermark 和隔离区。
- 建立版本化资产、拓扑、能力和规则制品。

退出条件：至少两类真实协议和一个业务源能形成同一作用域快照；可完整历史回放。

### Phase 2：可信快照和资源池

- 实现 SnapshotModule 和不可变 TrustedDecisionSnapshot。
- 建立多资源 CapabilityEnvelope、维护、人工接管和未完成命令视图。
- 市场、工艺和企业规则进入快照。

退出条件：缺失、冲突、过期、版本变化和时钟失步均有确定结果；资源池不依赖硬编码控制点。

### Phase 3：规划与独立认证

- 将 HiGHS/其他求解器作为 Planner adapter 正式装配。
- 完整传递时序计划和求解证据。
- 实现独立 CertifierModule 和数字孪生验证路径。
- 建立保守启发式降级计划，并同样经过认证。

退出条件：不可行、超时、数值异常和部分解不能进入执行；高风险场景通过 HIL。

### Phase 4：模型 Harness 与 LLM

- 建立模型注册、ContextPackBuilder、工具能力、预算和封闭输出。
- 把 skill、prompt、loop、检索和模型作为一个签名制品。
- LLM 只生成 ObjectiveCandidate、解释和证据引用。
- 上线影子、canary、abstain 和回滚机制。

退出条件：prompt injection、证据伪造、越权工具、无限 loop 和模型不可用不会产生控制动作。

### Phase 5：企业、市场和联邦规模化

- 上线能力包、承诺、跨站分层优化和隐私边界。
- 建立真实市场接入、对账和断网策略。
- 完成容量、HA、灾备、故障域和多租户隔离验证。

退出条件：站端断云保持安全自治；跨站失败不会破坏局部控制；性能达到已声明的 SLO。

- [ ] 硬约束是否不能被任何权重覆盖？
- [ ] LLM 是否只生成类型化候选并能够 abstain？
- [ ] 求解器是否保留原始状态、完整解、gap 和残差？
- [ ] 是否由独立实现复算硬约束？
- [ ] 模型、prompt、skill、工具和数据版本是否完整记录？

- [ ] 幂等记录是否反映真实执行生命周期？
- [ ] 发送、ACK、设备执行、回读和目标达成是否明确区分？
- [ ] 无法确定物理效果时是否停止盲目重试并进入对账？

### 降级和恢复

- [ ] 每个外部依赖是否有检测、降级、禁止事项和恢复条件？

- [ ] 是否通过负载、历史回放、fuzz、故障注入、HIL 和长稳测试？
- [ ] 是否能够原子发布兼容的规则、schema、拓扑、模型和 binding？
- [ ] 高风险规则和模型是否职责分离、双人审批、可回滚？
- [ ] 是否声明而不是猜测吞吐、P99 延迟、允许丢失和恢复 SLO？

## 26. 用户原始关注之外必须补充的问题

除了可扩展、可验证、边界、降级、门禁和模型约束，还必须补充以下问题：

1. **时间语义**：没有 event time、watermark 和时钟健康，异构数据无法正确融合。
2. **单位与控制语义**：数值正确但单位、方向或连续/离散类型错误，仍会导致危险动作。
3. **不确定性**：预测和测量必须携带区间，不能只传一个确定值。
4. **拓扑与能力版本**：设备在线不代表当前可控；计划必须绑定当时拓扑和能力。
5. **数据与模型供应链**：模型、prompt、skill、规则和映射都可能成为攻击或错误来源。
6. **人工接管与控制权仲裁**：必须定义谁在何时拥有最终写权限，以及如何安全归还控制权。
7. **物理执行的非原子性**：多设备控制需要 Saga、补偿和再优化，不是数据库事务。
8. **责任与解释**：解释必须引用真实 GateEvidence，不能把 LLM 的自然语言当成审计证据。
9. **隐私和数据主权**：联邦资源应共享能力包而不是默认共享工艺和原始遥测。
10. **生命周期和退役**：设备、点位、规则、模型和证书退役后，历史计划仍须可重放。
11. **安全与收益冲突**：必须使用严格优先级，而不是把安全写成一个高权重目标。
12. **恢复正确性**：系统重启、主备切换和网络恢复后，必须先恢复租约、序号、未完成命令和物理状态，再恢复自动控制。
13. **可运维性**：操作员需要看到系统为何拒绝、为何降级、当前谁拥有控制权，而不仅是模型解释。
14. **成本边界**：数据保留、模型推理、求解复杂度和场景数量必须有预算，防止“海量”演变为不可控成本。

## 27. 需要后续量化的决策

架构可以先确定，但以下数值必须由真实站点、设备和业务清单驱动，不能在本文中虚构：

- 各控制层的 deadline、抖动、WCET 和安全裕度。
- 持续/峰值点数、事件率、波形带宽和历史保留期。
- 每类数据最大新鲜度、乱序窗口和允许缺失比例。
- 每类优化问题规模、求解 deadline、允许 gap 和场景数量。
- 不同风险动作的自动化级别和人工审批阈值。
- 联邦能力包粒度、更新频率、隐私和合同责任。
- HIL 设备矩阵、故障覆盖目标和生产发布 SLO。

这些参数应进入版本化的 `OperationalProfile`，并成为 Gate 和测试 Harness 的输入，而不是散落在代码常量中。

## 28. 最终架构判据

当且仅当以下断言成立，EnerOS 才能务实地声称解决了“海量异构数据到正确执行策略”的问题：

> 任意外部数据或模型输出都不能直接获得设备控制权；每次决策基于一个不可变、可追溯、具有时效和不确定度的可信快照；硬规则不可被优化覆盖；LLM 只在受限 harness 中产生类型化候选；求解器输出由独立模块认证；只有 CertifiedPlan 能进入具有持久化、租约、幂等、回读和对账的执行链；任一依赖失败时系统进入明确、有界、可恢复的降级模式；最终结果以物理回读和状态收敛为准，而不是以模型、求解器或网络返回成功为准。
